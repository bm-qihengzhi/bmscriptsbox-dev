# README 与脚本描述（desc）规范

发布到社区 / GitHub 的脚本必须写 README。README 面向**普通用户（脚本使用者）**，不是开发者文档；同时 `info.desc` 会作为 GitHub 仓库描述和脚本库详情页简介，需符合 SEO。

---

## README 标准结构

模板源自真实脚本（视频抽帧）。前 5 段**必须**保留，其余按需选段。

```markdown
# 脚本名称

> 一句话简介：脚本是做什么的、基于什么引擎、有什么核心能力。

---

## 核心特性
（列出用户最关心的功能点，每行一个加粗要点）
- **特性一**：说明
- **特性二**：说明
- ...

---

## 脚本演示

![脚本名演示](./imgs/demo.gif "脚本名演示")

---

## 安装方法

本脚本的运行环境、依赖组件及图形化窗口均依赖"不忙脚本盒子"，建议仅通过盒子安装和使用本脚本。

> 前置条件：安装好 [不忙脚本盒子](https://www.bm-box.cn)

* 打开盒子 → **脚本市场** → 搜索 **「脚本名称」**
* 点击「安装」

  * 在文件管理器中选中文件，右键 → 选择脚本名称
* 快捷键启动
  * 为脚本设置全局快捷键，选中后按下即可执行
```

### 段落要点

| 段 | 必须 | 说明 |
| --- | --- | --- |
| 标题 + 一句话简介 | ✅ | 简介 = desc 的展开版，同时兼顾 SEO |
| 核心特性 | ✅ | 用户最关心的功能，加粗要点列表 |
| 脚本演示（GIF） | ✅ | **硬性要求**，见下方 GIF 占位规则 |
| 安装方法 | ✅ | 始终通过盒子安装 |
| 使用方式 | ✅ | 按触发方式（卡片/右键/快捷键）分小节写步骤 |
| 💡 使用提示 | 按需 | 参数含义、场景建议 |
| 节点脚本(开发者阅读) | 按需 | 声明了 node 才需要；放最末，避免打扰普通用户 |
| 🖥️ 环境要求 | 按需 | 系统 + 语言版本 + 外部工具表格 |

### 写作风格

- **面向普通用户**：多写操作步骤（在盒子里点哪里、选中什么文件、按什么快捷键），少写内部机制；节点/开发者内容单列并标注"(开发者阅读)"
- 演示 GIF 一张胜过大段文字；README 放 `imgs/demo.gif`，与 `bm-scripts-box-rc.toml` 同目录
- **同一个数字不能在文里指两件事**。真实踩过的坑：某翻译脚本简介写「在线 21 种」，使用提示又写「繁体中文、粤语等 21 种仅本地 AI 支持」——两个 21 含义不同（在线语言总数 / 仅离线语言数），读者会绕。正确写法是把两个数字都点明：「本地 AI 共 38 种，其中有 21 种……在线翻不了」。
  凡是语言数、格式数、支持数这类数字，**简介 / 核心特性 / 使用提示三处口径必须一致**，改一处就要回头扫全文
- **段名不要自创**。「快速开始」「启动方式」「功能一览」这类是好段名，但不是房子的段名——一律用模板里的 `## 安装方法` / `## 使用方式` / `## 核心特性`。段名统一是整套文档能被一眼扫读的前提

### 两条容易写错的惯例

- **图片目录**：全库实测统一是 `imgs/`（`./imgs/demo.gif`、`./imgs/demo.png`，`rc.toml` 的 `icon` 也指 `imgs/img.png`）。极少数脚本用 `assets/` 或 `images/`——那是历史遗留，新脚本一律 `imgs/`。
- **更新日志段**：**非必选，且旗舰脚本都没有**（实测 PDF加密 / 公众号下载 / 离线OCR / 视频格式转换 / 文件夹同步 全无此段）。README 讲「当前能做什么」，版本历史交给 GitHub Releases。真要在 README 留，就放**最末**、只留最近 1-2 版，别让历史盖过当前能力。

### 触发方式决定怎么写「使用方式」

模板里的 `### 右键启动` / `### 定时任务` 只在**脚本真的声明了对应触发器**时才写。按 `bm-scripts-box-rc.toml` 实际声明来：

| toml 里声明的 | README 该有什么子段 |
| --- | --- |
| 无特殊触发器、靠卡片点击 | `### 直接启动`（或 `### 卡片启动`） |
| 文件类输入（`inputs` 是路径） | 加 `### 右键启动`（在文件管理器选中文件 → 右键） |
| `[bmscriptsbox.schedule]` | 加 `### 定时任务` |
| `[bmscriptsbox.triggers.quick_copy]` | 加 `### 超级复制启动`，写清「选中 → 双击 Ctrl+C」两步 |
| 有 `params` | 加 `### 参数说明` 表格（参数名 / 说明） |

**照抄模板里的段名而无对应能力 = 造假**：用户按说明去右键选文件，发现没有这个入口。宁可少一段，不要多一段。

## GIF 占位规则

README **必须包含 GIF 演示**。新开发脚本暂无 GIF 时，**先占位引用**：

```markdown
## 脚本演示

![脚本名演示](./imgs/demo.gif "脚本名演示")
```

- 交付脚本时若未提供 `imgs/demo.gif`，需**明确提醒开发者补录**：用 ScreenToGif / LICEcap 录制一段展示核心操作的动图放入 `imgs/demo.gif`
- GIF 是脚本库详情页与 GitHub 仓库的门面，务必录制（一般 5~15 秒、展示完整操作流程）

## desc SEO 写法

`bm-scripts-box-rc.toml` 的 `info.desc` 会同时用于：
1. GitHub 仓库描述
2. 脚本库中该脚本详情页的网页介绍

所以 desc 要符合 SEO——**嵌入用户会搜索的关键词**，一句话概括功能与价值。

### 公式

```
[功能描述/一句话] | [关键能力点，用逗号或竖线分隔] | [输出结果/价值]
```

关键能力点尽量包含：处理对象（视频、图片、音频、文本…）、动作（抽帧、压缩、转换、翻译、提取…）、输出格式、批量/自动/一键等价值词。

### 参考示例（真实脚本）

```toml
# 视频抽帧
desc = "基于 FFmpeg 的视频抽帧脚本 | 支持按秒/按帧间隔/指定时间点、关键帧、智能抽帧(相似度去重),输出 PNG 图片序列,一键批量抽帧"

# 图片压缩
desc = "使用 sharp 库压缩选中图片，输出 JPG/PNG/WebP，批量处理"
```

### 要点

- **前置关键词**：开头即核心功能词（用户搜索时最先匹配的词，如"视频抽帧"）
- **能力点齐全**：把支持的抽帧方式/格式/模式都列出来，覆盖更多搜索意图
- **短句分隔**：用 `|` 或 `,` 分隔多个能力点，方便扫描阅读，也利于检索切词
- **控制长度**：GitHub 描述有长度限制，一句话能说完最佳；详版写进 README 简介
- **不要为搜索量塞与触发方式不符的词**：高频搜索词很诱人，但写着「划词翻译」而实际要「选中 + 双击 Ctrl+C」两步，用户按划词习惯操作后发现没反应，反而给差评。宁可放弃这个词，用真实动作词（「复制即译」「双击 Ctrl+C」）——**能搜到的词不如点进来不退货的词**
- **避免**：空泛形容词（"强大""好用"）、无关键词的废话
